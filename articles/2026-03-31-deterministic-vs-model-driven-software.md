# 從 deterministic 軟體到 model-driven 軟體

大部分工程師熟悉的，是 deterministic 軟體世界：同樣的輸入，在同樣的系統狀態下，得到同樣的輸出。規則由工程師明確寫死，流程可預測，可測試，也容易稽核。

這類系統很適合處理報表、權限、會計、庫存、訂單、金流等問題。工程師先定義世界如何運作，使用者只是沿著既定流程前進。

但很多真實問題本來就不適合完全寫死。

例如：

- 使用者現在最想看什麼內容
- 哪一則通知最可能被點擊
- 哪筆交易最像異常行為
- 這段文字該如何摘要
- 這位客戶現在最需要哪一種引導

這些問題的共同點是：它們本身帶有不確定性，工程師不可能事先列完所有 if/else。

因此，軟體的決策中心開始轉移。

過去是：

- 工程師寫規則
- 系統套規則
- 所有人走同一條流程

現在越來越多是：

- 系統觀察行為資料
- 模型推斷當下情境
- 介面與決策根據人與上下文動態調整

這裡常說的 non-deterministic，不是理論計算機科學裡那種嚴格定義，而是比較接近 probabilistic、model-based、data-driven 的系統：輸出不再單純由寫死規則決定，而是部分來自模型的機率推斷。

## 傳統客製化與模型驅動的差別

很多人會說，軟體以前也早就在做客製化。這句話只對一半。

以前的客製化通常是：

- 台灣區顯示繁中，美國區顯示英文
- VIP 客戶走 A 流程，一般客戶走 B 流程
- 管理員看見完整功能，一般使用者看簡化版

這些仍然是 deterministic。因為規則依然是工程師明確定義的。

模型驅動系統的差別在於：

系統不是只套用預先寫好的分支，而是從資料中學出權重、關聯與偏好，再對當下這個人做估計。

也就是說，系統不只是執行功能，而是在推測：

- 你屬於哪一類使用者
- 你可能在哪裡流失
- 你現在最需要哪一步
- 哪種排序最適合你

## 軟體工程的重心因此改變

在 deterministic 時代，工程師主要關注：

- 規則
- 流程
- 狀態機
- API
- 資料結構

到了模型驅動時代，除了上述內容，工程重心還會轉向：

- prompt 設計
- ranking 與 retrieval
- feedback loop
- evaluation
- guardrails
- fallback logic
- observability

也就是從「精確描述每一步」轉成「定義目標、上下文與邊界，讓系統在範圍內自行求解」。

## 不是所有東西都應該交給模型

這個轉變並不代表 deterministic 系統過時。

真正成熟的系統通常是分層的：

### 必須 deterministic 的部分

- 金流
- 帳務
- 權限
- 身份驗證
- 可稽核資料更新
- 法規遵循流程

這些地方需要穩定、可重現、可驗證、可追責。

### 可以 model-driven 的部分

- 推薦
- 排序
- 搜尋理解
- 文案生成
- 智能客服
- coding suggestion
- 互動式介面
- 風險預判輔助

所以現實中不是 deterministic 與 non-deterministic 二選一，而是：

**用 deterministic 系統保證底層正確性，用 model-driven 系統提升上層適配性。**

## 一句話總結

過去的軟體主要是把工程師寫好的規則，等比例套到每一個人身上；現在的軟體越來越像一個會觀察使用者、推測使用者、並根據情境調整輸出的系統。

更精確地說，這不是單純「AI 化」，而是：

**軟體正在從 rule-based software，轉向 model-mediated software。**
